# Pharmacy IT Management: Security and Data Model

## Authentication and Authorized Accounts

Firebase is not part of this implementation. The system will use **Supabase Auth with Google sign-in**. A signed-in Google account receives no operational access until an administrator marks its profile as approved. Supabase row-level security will scope each authenticated user to the records and actions permitted by their pharmacy role.

| Role | Primary responsibilities |
|---|---|
| `super_admin` | Account approval, user roles, migrations, high-risk administrative controls. |
| `it_supervisor` | IT operations, assets, helpdesk management, access provisioning, and operational approval. |
| `finance_manager` | Procurement review, budget controls, invoice reconciliation, and payment approval. |
| `asset_editor` | Asset registration, transfer, and lifecycle updates. |
| `document_manager` | Scoped Google Drive document operations. |
| `staff_viewer` | Their own tickets and access requests, plus permitted read-only views. |

## Data Boundaries

The database will have dedicated tables for user profiles, departments, locations, assets, asset movements, tickets, access requests, access approvals, immutable audit events, requisitions, purchase orders, goods receipts, invoice matches, renewals, meeting minutes, action items, documents, and system settings. Operational data belongs in Supabase; document bytes remain in Google Drive, while the system stores only permitted metadata and Drive IDs.

## Critical Workflow Guarantees

Asset codes will be generated by a database transaction against a protected code sequence, rather than calculated in the browser. Access-request audit events will be append-only: normal application roles can read them but cannot revise or remove prior entries. Procurement reconciliation will compare the purchase-order quantity and value, received-goods quantity and value, and invoice quantity and value before a match can be marked approved.

## Google Drive Scope

The application server will use a Google service account only for document actions. Every list, upload, and deletion request will verify that the target file or folder belongs to the configured root folder. The service account itself must be shared with only that folder; no client browser receives Google service-account credentials.

## Required Production Configuration

The integration needs the Supabase project URL, Supabase publishable browser key, server-only Supabase secret key, Google Drive service-account JSON, and the authorized Google Drive root-folder ID. All values will be placed in secure environment settings rather than source code.
